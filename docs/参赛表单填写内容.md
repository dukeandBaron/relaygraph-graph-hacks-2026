### Project title

RelayGraph — Follow the change, verify the next step

### Description

```text
RelayGraph helps small activity organizers recover from changed requirements without treating old confirmations as current. In a synthetic makers-showcase example, bringing a registration deadline forward affects registration, travel and catering through three dependency hops; an unrelated accessibility check remains current. The application queries FalkorDB for those paths, previews the impact, then adopts a reviewed correction with a revision-bound, idempotent write. It preserves original notices and old receipts, creates review actions with owners, and shows the exact evidence path behind each action. FalkorDB is the sole state store; a database outage stops actions instead of returning a substitute demo. This is new event-period implementation inspired by prior notice-review domain experience. Development was assisted by Codex. The default runtime is an explicit graph policy, not a language-model service; optional read-only MCP tools expose graph context to a caller's AI assistant. All demo people, events and receipts are synthetic. Full local setup is provided.
```

### How did you use FalkorDB in your project?

```text
FalkorDB is the only application state store. SourceRevision, Requirement, Task, Person and Artifact nodes hold the connected context; ReviewAction and Operation nodes preserve the action trail. Parameterized Cypher traverses one to six DEPENDS_ON edges to identify direct and indirect impact and retrieve owners and original source text. The correction proposal is bound to a workspace, graph revision, changed values and affected record IDs. Adoption recomputes that basis and uses one compare-and-set write to update the current requirement, append a source revision, mark old confirmations and receipts for review, create owner-linked review actions and log an operation digest. Duplicate commands do not create duplicate actions; changed commands, stale previews and proposals from another workspace are rejected. Original source text remains available separately from current requirement values. Database outage and container restart were tested against real FalkorDB. The browser exposes draggable relationships, impact previews, evidence paths and the exact queries. Read-only MCP tools let an external AI assistant retrieve the same context without receiving arbitrary Cypher or write access.
```

### What did you like about FalkorDB?

```text
Parameterized multi-hop Cypher made the dependency paths easy to inspect and verify. We could keep task context, immutable source text, old confirmations and new review actions in one connected store. Separate graph names also made isolated synthetic workspaces straightforward. Real restart and outage checks let us show where the graph is essential to the product.
```

### What improvements would you like to see in FalkorDB?

```text
I would value a minimal official example for revision-bound action plans, idempotent graph writes and immutable source history, together with concise client retry/TLS configuration examples and Windows-friendly container setup notes. Those examples would help prototype builders preserve evidence and handle interrupted updates correctly.
```
